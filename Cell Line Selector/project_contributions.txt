PROJECT CONTRIBUTIONS
Cell Line Selector: Multi-Omics Data Cleaning, Harmonisation, Integration and Validation

Prepared from the implemented source code, pipeline scripts, tests, generated outputs and audit files in this project.

======================================================================
1. OVERALL PROJECT CONTRIBUTION
======================================================================

I developed an end-to-end data processing and analysis framework for a cell-line selection system based on multiple biological data sources. The project brings together transcriptomic, proteomic, metabolomic, microRNA, mutation, fusion, copy-number, cancer-gene and cell-line metadata into a consistent analytical resource.

My overall contribution was to transform heterogeneous raw biomedical datasets into cleaned, human-cell-line-focused, identifier-harmonised and analysis-ready data products. I also implemented statistical methods for transcriptomic and protein-level integration, created reproducible DuckDB outputs, and developed audits and figures to assess data quality, missingness, scale, coverage and cross-source consistency.

The main contributions are:

- Designing a staged data-processing workflow from raw files to cleaned data, harmonised rosters, DuckDB tables and analytical scores.
- Developing dataset-specific cleaning routines for heterogeneous biomedical formats.
- Removing non-human cell-line records using an explicit identifier-based procedure.
- Harmonising cell-line, gene, UniProt, COSMIC and model identifiers across sources.
- Restricting expression data to canonical protein-coding genes.
- Implementing transcriptomic scale detection, detection-floor handling, robust standardisation and cross-source score integration.
- Implementing two alternative protein-scoring strategies, including platform agreement and isoform handling.
- Building quality-control audits for identifiers, species, missingness, mappings, numerical summaries and generated scores.
- Producing publication-oriented figures for distributions, scale harmonisation, missingness, calibration and pipeline structure.
- Adding caching, chunked computation, logging, Parquet storage and DuckDB access to improve scalability and reproducibility.

2. RAW DATA DISCOVERY AND DATA LOADING
======================================================================

I implemented the raw data ingestion stage in pipelines/00_data_loading.py. This stage provides a general mechanism for discovering and loading heterogeneous input files rather than relying only on manually listed files.

My contributions include:

- Recursive discovery of CSV, TSV, TXT and GCT files under the raw-data directory.
- Curated parsing rules for known data sources and file types.
- Automatic derivation of dataset keys from input files.
- Conversion of selected tab-delimited inputs into a consistent tabular representation.
- Initial previews of loaded datasets, including shape and missing-value summaries.
- Conversion of loaded raw tables into Parquet files under data/raw data/parquet/.
- Error handling that allows the loading stage to continue after an individual file failure while recording the failure in the project logs.

I also centralised project paths and raw-data access in src/scripts/data_utils.py. This provides shared paths for raw data, cleaned data, CSV exports, DuckDB, and EDA reports, reducing the risk of different scripts using inconsistent locations.

The raw loading design was important because the project contains both narrow tables and very wide molecular matrices. Parquet provides a compact, column-oriented intermediate format that can be queried efficiently by DuckDB and avoids repeatedly parsing the original raw text files.

4. HUMAN CELL-LINE FILTERING
======================================================================

I designed and implemented an explicit human-origin filtering process rather than relying on cell-line names alone. This work is implemented in clean_cellosaurus() and filter_non_human_rows() in src/scripts/cleaning_functions.py.

The filtering contribution includes:

- Detecting human origin using taxonomic and textual species information.
- Treating blank or missing species information as non-human for conservative filtering.
- Retaining mixed human/non-human records where the record indicates human relevance.
- Building a CVCL-based non-human blocklist.
- Filtering records using CVCL IDs, Cellosaurus IDs and CVCL identifiers extracted from RRIDs.
- Avoiding name-only filtering because cell-line names can collide between human and non-human records.

This identifier-led approach reduces the risk of incorrectly removing human cell lines or retaining non-human records because of ambiguous names.

I added independent quality-control scripts to assess this decision:

- audit.py independently rebuilds the non-human blocklist and scans cleaned Parquet or CSV outputs for leaks.
- The audit classifies datasets as CLEAN, LEAK or NO_ID_COL and can save leaked rows under logs/audit_leaks/.
- hono_sapeins_check.py examines collisions between human and non-human names and synonyms, identifies short high-risk names and estimates possible downstream impact.

These audits make the biological filtering decision inspectable rather than leaving it as an implicit preprocessing assumption.

5. CELL-LINE AND GENE IDENTIFIER HARMONISATION
======================================================================

I implemented the cross-source harmonisation layer in src/scripts/harmonisation_functions.py and orchestrated it through pipelines/02_data_harmonisation.py.

Cell-line harmonisation contributions include:

- Extracting CVCL identifiers from RRIDs.
- Detecting ACH-style model-ID columns.
- Normalising cell-line join keys, including forms such as A-375, A 375 and A375.
- Aggregating multiple identifiers into sorted semicolon-separated lists.
- Building a one-row-per-model cell_line_roster.
- Adding Cellosaurus synonyms and CVCL mappings.
- Expanding CVCL IDs from exact cell-line names where appropriate.
- Attaching model IDs back to cleaned source tables.
- Resolving model IDs through names, CVCL IDs, RRIDs, protein matrices and model lists.
- Recording ambiguous mappings and row-count changes.

Gene harmonisation contributions include:

- Building gene-name aliases from mutations, fusions and HPA data.
- Constructing a one-row-per-gene gene_roster.
- Normalising Ensembl identifiers.
- Filtering expression matrices to roster-approved canonical ENSG identifiers.
- Restricting expression analyses to protein-coding genes.
- Backfilling genes that are available only in proteomics data.

External identifier bridge contributions include:

- Bridging UniProt identifiers to gene identifiers.
- Linking ProCan protein identifiers to the common gene representation.
- Adding COSMIC copy-number bridges.
- Adding Cancer Gene Census bridges in both directions.
- Attaching model identifiers to relevant cleaned tables.

The harmonisation pipeline also produces summaries of model-ID attachment, ambiguous mappings and orphan entries. The inspected outputs include a cell_line_roster of approximately 1,840 rows and a gene_roster of approximately 20,089 rows. The recorded attachment summary reports no row duplication in the summarised outputs.

I implemented a scalable EDA framework in src/scripts/eda_functions.py and orchestrated it with pipelines/04_eda.py.

The EDA framework includes:

- Schema inspection and row-count queries.
- Numeric-column detection from DuckDB types.
- Chunked aggregation over wide tables.
- Cached missing-value reports.
- Cached numeric summaries.
- Missing-value bar charts.
- Missingness matrices.
- Missingness heatmaps.
- Missingness dendrograms.
- Little's MCAR testing.

- Numeric summary statistics.
- Scale-profile detection.
- Distribution grids.
- Boxplot grids.
- Scale comparisons.
- Correlation heatmaps.
- Gaussian-per-column summaries.
- Cross-table missingness summaries.

I made the EDA implementation suitable for large and wide tables by:

- Querying statistics through DuckDB aggregates.
- Processing columns in chunks.
- Using bounded row-level samples only where plots require actual values.
- Avoiding full pandas materialisation of very wide matrices.
- Caching per-table reports to disk.
- Supporting a --force option to invalidate cached statistics.

The EDA pipeline registers cleaned Parquet files as DuckDB views. This means the analysis reads data from disk on demand and remains practical for datasets such as expression and proteomics matrices.

I also added a dedicated raw-value facet generator in pipelines/05_raw_value_distributions.py. This produces small histograms for raw measurement distributions across datasets, excludes obvious identifier and coordinate fields, bounds the number of sampled values, and limits column batches for extremely wide tables.

The project now contains generated EDA outputs for raw-value distributions, fitted Gaussian summaries and cross-table missingness.

10. TRANSCRIPTOMIC STATISTICAL INTEGRATION
======================================================================

The canonical transcriptomic implementation is in src/scripts/transcriptomics.py and is orchestrated by pipelines/05_transcriptomics_stats_layer.py. I implemented or assembled a statistical layer that combines transcriptomic measurements from HPA, DepMap and GEO while accounting for differences in measurement scale, detection and processing method.

The transcriptomic contributions include:

- Parsing GEO SOFT records from geo_meta/GSM*.txt.
- Extracting platform, processing, series, title, source and sample metadata.
- Classifying processing methods such as GC-RMA, RMA, MAS5, PLIER, dChip, VSN and RNA-seq.
- Building GEO method axes from platform ID and processing family.
- Combining HPA, DepMap and GEO measurements.
- Resolving profile IDs and GSM IDs to common model IDs.
- Restricting genes to canonical ENSG identifiers in gene_roster.
- Empirically detecting whether a measurement is linear or log-like.
- Applying log2 transformation to linear measurements.
- Collapsing replicates by cell line and method using medians.
- Estimating detection floors.
- Calculating lineage-specific detection fractions.
- Computing robust median/MAD z-scores.
- Using rank inverse-normal scores for censored regimes.
- Withholding below-detection and no-data values as missing rather than treating them as ordinary measurements.
- Shrinking lineage-specific scales toward global scales.
- Combining source-level evidence using Stouffer-style methods.
- Combining cross-source evidence using equal-weight Stouffer aggregation.
- Writing large outputs to DuckDB in chunks.
- Verifying generated outputs and recording diagnostic summaries.

I also implemented seeded calibration over floor_q, n0, upper_cut and lower_cut. The calibration evaluates held-out cross-source Spearman concordance and supports one-standard-error parameter selection.

The selected parameters recorded in results/transcriptomics/chosen_params.json are:

- floor_q = 0.2
- n0 = 100
- upper_cut = 0.6
- lower_cut = 0.2

The generated calibration grid contains 480 parameter combinations. Existing outputs include grid-search results, chosen parameters, diagnostics, coverage plots, floor plots, status-by-lineage plots and n0-sweep plots.

12. PROTEIN SCORING METHOD 1
======================================================================

I implemented a first protein-scoring approach in pipelines/06_protein_score M1.py and supporting code in Protein M1/platform_tier.py and Protein M1/protein_scorer.py.

The Method 1 contribution includes:

- Building UniProt and gene-symbol to ENSG mappings from gene_roster.
- Converting protein matrices to long format.
- Computing lineage-conditioned robust z-scores.
- Calculating ProCan and CCLE per-protein Spearman correlations.
- Requiring a minimum of 30 shared cell lines for correlation assessment.
- Assigning proteins to consistent, cautious or conflicting tiers.
- Removing CCLE values for conflicting proteins.
- Combining retained source scores with coverage-weighted Stouffer aggregation.
- Writing a protein_z DuckDB table.

The standalone platform-tier implementation and the older protein_scorer.py provide alternative or legacy routes for deciding whether both platforms or ProCan alone contribute to a protein score.

13. PROTEIN SCORING METHOD 2
======================================================================

I implemented a second protein-scoring approach in pipelines/06_protein_score M2.py. This method extends the first approach by handling isoforms and platform disagreement more explicitly.

The Method 2 contribution includes:

- Handling multiple protein IDs that map to one gene.
- Computing pairwise isoform Spearman agreement.
- Using the maximum isoform value when isoforms are concordant.
- Using the mean when isoforms are discordant or cannot be assessed.
- Treating ProCan and CCLE symmetrically.
- Deriving isoform and platform-agreement thresholds from null and matched distributions.
- Using power-based minimum-overlap thresholds.
- Converting platform disagreement into a confidence multiplier rather than simply discarding one platform.
- Writing protein z-scores and isoform-quality-control data to DuckDB.

I also added audit_protein_z.py to report the schema, dimensions, z-score summaries, source coverage and lineage counts of a generated protein z-score table.

The source code demonstrates that both methods were implemented. The inspected workspace did not contain generated protein-score artifacts in the visible results or figures directories, so successful end-to-end execution of every protein stage should be described as implemented rather than independently verified from an output artifact.

17. RESEARCH AND ENGINEERING VALUE OF THE CONTRIBUTION
======================================================================

The main research value of my contribution is the creation of a common analytical framework for comparing and integrating data generated by different technologies, platforms and processing methods. The system does not treat all numeric values as directly comparable. It first addresses identifier compatibility, species filtering, measurement scale, detection limits, missingness and source agreement.

The main engineering value is scalability and traceability. Wide molecular matrices are handled through Parquet, DuckDB, chunked aggregation and bounded sampling. Data-processing decisions are recorded through logs, audit tables, numerical summaries and provenance notes. The staged design also allows individual components such as cleaning, harmonisation, transcriptomic integration, protein scoring or EDA to be rerun and inspected separately.

The work therefore contributes both:

- A cleaned and harmonised multi-omics data resource for cell-line analysis.
- A reusable computational framework for quality control, scale harmonisation and evidence integration.

18. LIMITATIONS AND ITEMS TO VERIFY
======================================================================

For accuracy, the following points should be checked before making final claims in a dissertation:

- The project contains both current and stale transcriptomics implementations. The canonical statistical implementation is in src/scripts/transcriptomics.py and pipelines/05_transcriptomics_stats_layer.py; stale files should be clearly labelled or excluded from the final workflow.
- Protein Method 1 and Method 2 are both implemented, but the inspected workspace did not contain visible generated protein-score artifacts proving successful execution of every stage.
- The current requirements file does not declare all imported scientific and plotting packages.
- The focused test file may be stale because two imported helper functions were not found in the current harmonisation implementation.
- The numerical audit records an extreme z_lineage maximum of approximately 9.4e9. This should be investigated as a possible numerical edge case or defect before reporting the z-score results as final.
- Git status includes changes outside the audited subdirectory, so historical authorship attribution should not be inferred solely from the surrounding repository state.

These are not omissions from the implemented contribution; they are verification points that improve the precision and defensibility of the final report.

I developed an end-to-end multi-omics data cleaning, harmonisation and integration framework for the Cell Line Selector project. I implemented raw-data discovery and conversion, dataset-specific cleaning, human cell-line filtering, cell-line and gene identifier harmonisation, external identifier bridges, DuckDB data loading and scalable exploratory data analysis.
